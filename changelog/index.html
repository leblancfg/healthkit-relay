    Changelog¶

    Notable changes to the server and the app. Versions follow Semantic Versioning; server releases and the app are versioned separately.

    Unreleased¶

    App 1.0.0 (14), for the App Store¶

    • The server's address follows the server: when a paired server names a preferred https address (its -public-url), the app checks that the address answers as the same server (same server ID, without the token, then its token as the same device) and moves there, with its history and sync positions. Redirects are not followed. An address that does not answer as the same server is tried again after 6 hours.
    • A setup link for the address the paired server names as its preferred one pairs without asking, as the same device, with its sync positions: before, a new address meant a new device and a full upload again. A link for any other address asks first, as before.
    • Enter Server Details Instead takes the setup code shown on the setup page, as well as the admin token.
    • The welcome screen says what the app works with: a server you run yourself, with a link to the setup guide. Links to the privacy policy and help on the welcome screen and in Advanced.
    • Pending uploads, sync positions and the log stay out of iCloud and computer backups.
    • Erase Server Data and Disconnect (Advanced): stops syncing, has the server delete everything this iPhone sent, and disconnects.
    • Disconnect stops the running sync and the uploads iOS carries on; a new pairing with another server (also after a disconnect) sends the whole history again.
    • Every request that carries the token goes only to the server's address: redirects are refused, and an upload iOS's background session redirected elsewhere counts as not sent.
    • Plain HTTP only to addresses on the local network (private, link-local and Tailscale IPs, .local and single-label names); every other server takes HTTPS.
    • Each step that waits on the network (pairing, token upgrade, erase, status) changes the connection only if the user did not disconnect or set up another server meanwhile; sync positions move only on the connection their upload went to.
    • A setup accepted before a disconnect or an erase does nothing after it, even when it was waiting behind another setup; the address handoff moves the app in one step with disconnect and pairing. Every sync position (pages, empty pages, activity summaries, effort relationships, uploads finishing later) moves only for its own connection and set of positions, which every reset renews.
    • The server address and token are one Keychain item, read and written in one step. Erasing and setting up never overlap: a setup link opened during an erase is refused, and an erase waits for a setup. The app moves to the server's preferred address only when no setup or erase runs, and a preferred address counts only for the connection whose server named it.
    • A new install starts unpaired: a server address and token an earlier install left in the Keychain are cleared on first start.
    • Privacy manifest (PrivacyInfo.xcprivacy): no tracking, no collected data, the reasons for UserDefaults and file metadata.
    • The App Store build reads no clinical data: Health Records and CDA documents are left out (a build of your own can read them, see ios/README.md).
    • Info.plist: the local network permission explains itself, export compliance is declared (HTTPS only), and the app requires HealthKit.

    0.7.0 (2026-10-25)¶

    The first server release on GitHub Releases: binaries for Linux, macOS and FreeBSD (amd64 and arm64) with the systemd unit, and checksums.txt.

    Server 0.7.0¶

    • An upload already under way when an erase of its device finishes is refused (409) instead of bringing data back; DELETE /v1/data?disconnect=1 also revokes the device's token in the same step (the app's Erase Server Data and Disconnect).
    • A server ID per archive (server.json) and the preferred address in GET /v1/status and in the answer to each heartbeat (now 200 with JSON); GET /v1/server answers the ID without a token. Phones move to -public-url on their own.
    • Demo mode (-demo-code-file, -demo-reset, -demo-quota): a shared setup code that pairs any number of iPhones and an hourly upload quota.
    • Requests through Tailscale Funnel count as public for -setup-from private, and /metrics answers private networks only.
    • The demo server stores nothing about its users: batches are checked, answered and dropped; devices get signed tokens (30 days) instead of entries in devices.json; no per-request log lines; upload bytes, concurrent uploads and pairings are capped per hour.
    • The public demo server moved to https://health-relay-demo.leblancfg.com: the demo mode as a Cloudflare Worker (demo/worker), checked against the Go server's by one request suite (demo_contract_test.go, in CI under wrangler dev). https://health-relay.leblancfg.com leads to this documentation.
    • Metrics forwarding refuses redirects. State files are synced with their directory, so a revocation survives a power loss. Erasing a device with nothing stored returns at once. Setup page forms without Fetch Metadata must carry the page's own Origin.
    • Docker Compose: Grafana listens on this computer only unless GRAFANA_BIND says otherwise.

    • github.com/klauspost/compress 1.18.7 (GHSA-259r-337f-4rfw).

    • Counts app 0.7.0's triggers under their own names in healthkit_relay_batches_total, healthkit_relay_heartbeats_total and the last-batch and last-heartbeat timestamps: processing, urlsession, backgrounded and continued. Older apps are unaffected; an older server counts these as unknown.

    • The heartbeat line says plugged in or on battery, low power mode and background app refresh denied or restricted, from app 0.6.4's heartbeats; older apps' lines are unchanged.
    • POST /v1/heartbeat (an upload token): logs the app's heartbeat in one line, and counts it in healthkit_relay_heartbeats_total{trigger} and healthkit_relay_last_heartbeat_timestamp_seconds{trigger}.
    • healthkit_relay_last_batch_timestamp_seconds{trigger}: when the last batch of each trigger arrived.
    • Refused tokens are logged (at most every 10 seconds, with a count of the others): method, path, client address, user agent and a 6-character prefix of the token's SHA-256.
    • Query API, turned on with -query-duckdb: read-only endpoints for the type catalog, samples and daily or hourly aggregates, with time zones and Apple-style source de-duplication. The binary serves an OpenAPI 3.1 document at /openapi.json and Swagger UI at /docs. Each query runs in a locked-down duckdb process. See Query API.
    • The OpenAPI document describes type as a string with a pattern and examples, in place of an enum of every HealthKit identifier; GET /v1/types lists the valid values. An unknown type answers 400 with the closest names: unknown type HKQuantityTypeIdentifierSteps; did you mean HKQuantityTypeIdentifierStepCount?. Kinds stay an enum, each described in one line. GET /v1/kinds is removed: GET /v1/types?kind=category lists the types of one kind. The served document goes from 67 kB to 54 kB.
    • Token scopes: a read token (from the setup page, healthkit-relay token create or POST /v1/tokens) queries and does nothing else; a paired device's token uploads and gets 403 on queries. Existing devices.json files keep working as they are.
    • The admin token (formerly the server token): the server generates it on first start, 256 random bits, and prints it once to its log with the setup page's address (docker compose logs relay, journalctl -u healthkit-relay). <archive-dir>/admin.json holds its SHA-256.
    • healthkit-relay admin reset prints a new admin token; the running server switches to it at once and signs out browsers signed in with the old one.
    • pair, devices, revoke, token create and admin reset work on the state files in the archive directory (-archive-dir), with file locks, while the server runs; this replaces their -token-file and -server flags. Run them as the server's user or as root, e.g. docker compose exec relay healthkit-relay pair.
    • Setup codes are kept as SHA-256 in codes.json and last across a restart until they expire.
    • -token-file (HKR_TOKEN_FILE) is optional and deprecated: at start, the server imports an existing server token file into admin.json and logs a warning; then delete the file and the flag. The Compose file mounts no token file; the image still imports /run/secrets/hkr_token when an earlier install mounts one.
    • Uploads and status requests with the admin token are deprecated: still accepted, logged at most hourly and counted in healthkit_relay_admin_token_uploads_total. Pair such apps again from the setup page.
    • Setup page: Sign in with the admin token, with where to find it; Pair your iPhone, Paired devices and Read tokens; copy buttons for a new read token and the setup code's link.
    • Reworded output: the first-start log says Setup page: (formerly Sign in at:), and the devices column PAIRED is now CREATED.
    • NixOS: healthkit-relay-ctl runs any command with the service's settings (sudo healthkit-relay-ctl pair, admin reset, ...). tokenFile is deprecated; the module imports a /var/lib/healthkit-relay/token from its earlier versions once.

    App 0.7.0¶

    • Every background mechanism iOS offers, layered: HealthKit background delivery, the background app refresh (now asked for 15 minutes ahead, and again at launch, after each sync, when the app goes to the background and after each run), and a new processing task that iOS may run while the iPhone charges and has a network. iOS decides when each runs. The processing task usually runs while the iPhone is locked, when Health data is locked too: it then notes a sync as owed for the unlock.
    • Uploads that outlive the app's background time. Each batch is written to a file. With the app on screen it goes through a background URLSession, which iOS finishes even if you leave the app; in the background it goes out at once through a standard session, and the upload under way when the background time ends moves to the background session. When such an upload finishes, iOS wakes the app: the anchor that upload confirms is saved (only if no later sync moved it meanwhile, so positions advance only past data the server confirmed), and the app syncs on if the iPhone is unlocked.
    • Leaving the app runs one more sync, in the time iOS gives then (about 30 seconds).
    • iOS 26 and later: a first sync, or a Sync Now after 6 hours without a sync, goes on when you switch to another app. iOS shows its progress in a Live Activity, where you can stop it. Progress moves with every page sent, also within one long data type.
    • While the app runs, a sync that failed runs again as soon as the network comes back.
    • Heartbeats and batches name the new triggers: processing, urlsession, backgrounded and continued.
    • The app, README and docs say how often it syncs: in the background several times a day; open the app to sync right away. iPhone keeps Health data locked while the phone is locked, so background syncs happen after an unlock.

    App 0.6.4¶

    • Heartbeats say whether the iPhone was plugged in or on battery, in Low Power Mode, and whether Background App Refresh is on for the app: iOS weighs these before it wakes the app, and the server's log shows them with each heartbeat.
    • The app's log notes each lock, each move to the background and each change of power state while the app runs, and the power state at every launch, refresh and HealthKit wake.

    App 0.6.3¶

    • One sync at a time for everything that starts one. Opening the app sets off an unlock, the foreground sync and HealthKit wakes for many types within a second or two; in 0.6.2 these ran as separate syncs, so the sync animation ran several times in a row and the server got a heartbeat for each. Now they join the sync already running, which shows as one sync and sends one heartbeat, tagged with what started it.
    • A HealthKit wake waits 1.5 seconds before syncing, so the rest of its burst joins it. New data for a type the running sync has read already makes one more pass over just that type.
    • Each HealthKit wake is answered once its type was read, at the latest after 20 seconds.

    App 0.6.2¶

    • Background sync that keeps running: every HealthKit wake syncs all types, in one sync shared by all the wakes that arrive together (opening the app or an unlock fires a few hundred), where 0.6.1 started one sync per type. iOS counts each wake against the app's background time, and stops waking an app that does not answer HealthKit.
    • When iOS ends the app's background time, the app answers HealthKit's open wakes and stops the sync, which the next wake finishes. In 0.6.1 a sync cut short waited, unanswered, until iOS ran the app again, which could be hours.
    • HealthKit may wake the app at once for new heart rate, steps, active energy, walking distance and sleep data, so it runs soon after an unlock; other types stay at most hourly.
    • A heartbeat to the server at the end of each background wake, also when the iPhone was locked or the upload failed: what woke the app, whether Health was readable, the outcome, the last error and the background time left. See No syncs in the background.

    App¶

    • Welcome, pairing, Health access, status and error texts use the server's terms (server address, setup page, setup code, admin token, paired device), and each error says what to do next. Manual setup asks for the Admin token.

    0.6.1 (unreleased)¶

    Server¶

    • Batches may say what started the app's sync (trigger) and the app's state (app_state): both appear in the batch v2: log line, and healthkit_relay_batches_total{trigger} counts batches by trigger (unknown for older apps).

    App 0.6.1¶

    • Background sync works: observer queries are set up synchronously at launch from the types the app asked for (saved when it asks), with no HealthKit status call first, so a launch on a locked phone no longer ends with nothing observed.
    • An authorization plan or readable-type list HealthKit could not fully answer (phone locked) is no longer kept for the life of the process; it is computed again at unlock and when the app opens.
    • A sync skipped while locked, or failed, is remembered across launches and run at the next unlock, background refresh or open.
    • A background app refresh about hourly runs a full incremental sync as a fallback.
    • Each batch says what started it (foreground, observer, refresh, unlock, retry). Each observer wake is logged with the app's state and whether protected data is readable.

    0.6.0 (2026-10-18)¶

    Server¶

    • Erasing requires ?confirm=erase; only the app before 0.6 may leave it out.
    • An archive directory, or parquet/ in it, that is a symlink works (systemd's DynamicUser makes /var/lib/<name> one): de-duplication and file modes no longer miss what is behind it. File modes are set only on what the store owns.
    • Line protocol escapes backslashes and control characters; paired device names refuse control characters; the setup page refuses cross-origin form posts, caps form size and cannot be framed.
    • Packaging: Docker image, release binaries with a systemd unit, a NixOS module with a VM test, and an end-to-end smoke test run on every install path in CI.

    App 0.6.0¶

    • Asks before sending Health data to a server it was not set up with, when a setup link names a new one.
    • Sends confirm=erase with Erase Server Data and Start Over.

    Docs¶

    • Documentation site, setup guides, security policy and contribution guidelines.

    0.5 (2026-10-17)¶

    Server 0.5.0 to 0.5.2¶

    • Storage: a SQLite staging database (durable before the 200, de-duplication on disk), flushed hourly to Parquet partitioned by dataset, type and month, compacted nightly, with deletions applied at compaction. DuckDB views in server/sql/views.sql.
    • migrate converts the JSON Lines archive of 0.4 and earlier; flush and compact run the maintenance at once.
    • DELETE /v1/data erases what a device uploaded, for good.

    App 0.5.0¶

    • Erase Server Data and Start Over.

    2026-10-17¶

    App 0.4.1¶

    • One setup change at a time, so a setup link opened at launch leaves a single paired device.

    Server¶

    • pair -valid <duration> for setup codes sent to a phone (default 15 minutes, at most a day).
    • Loopback addresses are never put in a setup code; the setup page offers the addresses it finds (the page's own address, Tailscale serve names, LAN and Tailscale IPs).
    • One-tap app setup: one-time setup codes, a QR code on /setup and in the terminal (pair), and per-device tokens that can be listed (devices) and revoked (revoke).
    • Records whose values are not {value, unit} are accepted; rejected batches are logged with the reason.

    App 0.4.0¶

    • A status screen, setup from a link or QR code, Health access in one step.

    App 0.3.0¶

    • No HealthKit exception can end the app; Health access is one sheet, per-object types are optional rows. Health Records became an opt-in step.

    0.2¶

    • Everything in HealthKit is synced, with the type list generated from the iOS SDK at build time (wire format version 2: workouts with routes, ECGs, heartbeat series, correlations, documents, activity summaries, characteristics).

    0.1¶

    • First version: a Go receiver with an append-only archive and line-protocol forwarding, and a SwiftUI app that syncs HealthKit incrementally in the background.
